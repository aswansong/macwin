# M1 可点击原型结论（第二轮）

状态：M1 可丢弃交互验证；不是生产实现、真实设备验证或新的系统能力承诺。

原型分支：`prototype/ui-flow-v1`。入口：`index.html`；代码：`prototype-ui-flow/`。所有数据和结果均为虚构，状态只保存在浏览器内存。

## 本轮回答的问题

第一轮原型把 Windows 与 Mac 的内部状态机直接展示为 8 个连续步骤，并在扫描页展示“发现、可迁移、已排除”和排除原因。负责人明确否定了这种表达：MacWin 的目标是少操作、少阅读，不是让用户学习迁移系统本身。

第二轮原型改为验证以下方向：

- 首页是否只需要“检测这台 Windows”和“在 Mac 导入配置”两个入口；
- 每个平台是否只显示 3 个用户阶段，而不展示 8 个内部处理节点；
- 扫描结果是否应只显示可继续处理的具体内容，不显示排除数量和排除原因；
- “键盘与输入＋鼠标与触控板”是否适合归为“操作习惯”，“软件＋开发”是否适合归为“软件与开发”；
- 选择页是否可以把标题、解释和风险标识放在同一行，取消“查看细节”和“已选择/未选择”重复文案。

## 已被否定的第一轮方案

- **8 步全局进度条**：把导出端、文件交接和导入端混成一条企业式流程，增加心理负担。
- **扫描统计表**：只有数字，没有回答“具体发现了什么”；排除原因让用户把注意力放在不能做的事情上。
- **五组过细分类**：键盘、指针、软件和开发分别占行，增加了类别数量但没有帮助决策。
- **卡片式问卷**：每项重复显示“已选择（演示）”“查看细节”，让 5 个简单勾选占据整页。
- **始终展开的原型工具栏**：原型控制压过产品本身，容易被误认为用户功能。

## 第二轮采用的交互假设

- 首页提供两个直接入口：Windows 开始兼容检测；Mac 直接导入 `.habitpack`。
- Windows 端只显示“检测、选择、导出”，Mac 端只显示“导入、确认、完成”。权限、快照和验证仍存在于状态机，但不作为额外用户阶段展示。
- 检测完成页只显示四组具体内容：操作习惯、软件与开发、系统设置、Wi‑Fi。未迁移项目保持安静，不提供排除原因入口。
- 选择页保留 5 个真正需要确认的选项，并继续遵守既定默认值；每项只占一行，说明直接跟在标题后面，风险标识保持首层可见。[D-006、D-007、D-019]
- Mac 计划页继续强制确认，但默认按五个用户可理解模块显示一句结论；原因、收益、例外和恢复方式按需展开。[D-010]
- 原型场景控制默认折叠到右下角，不参与正式产品信息层级。

这些是假设和负责人方向的原型化表达，仍需要负责人再次浏览或真实新手测试后才能写入 `main` 的正式产品决定。

## 仍然成立的安全与状态结论

- 强制计划确认位于 Mac 导入检查之后、模拟执行之前；状态机与测试都拒绝跳过计划直接执行。[D-010]
- `含敏感信息`、`需管理员`、`第三方工具`、`不可自动恢复` 使用文字标签，不只依赖颜色。[D-011、D-019、D-021]
- 权限拒绝、离线、第三方拒绝和单模块失败不会被汇总成“迁移完成”。[D-014、D-026]
- 恢复始终描述为“迁移前状态”，不称为恢复出厂设置。[D-012]

## 尚未验证

- 尚未验证第二轮精简流程是否已经达到普通 Windows 用户所需的信息量；需要负责人复查和目标用户任务测试。
- 尚未验证真实平台接口、UAC/TCC、ZIP 解析、快照、软件安装、网络写入、第三方供应链或任何真实系统结果。[D-022、D-023]
- 没有证据证明未加密 `.habitpack` 中的真实 Wi‑Fi 凭据可被安全迁移；OD-005 继续阻断真实凭据实现。[D-019]
- OD-001、OD-004、OD-007、OD-010 等公开支持、正式品牌、第三方供应链和报告格式仍未决定。

## 安全与范围声明

原型没有读取或修改 Windows/macOS 设置、注册表、Wi‑Fi 密码、真实软件或个人数据；没有 UAC、TCC、Karabiner-Elements、LinearMouse、Homebrew 或其他安装；没有外部网络请求、外部 API、账号、后端、数据库、原生桥接、Shell、PowerShell、自动更新、安装包或 Release。它不会生成或导入真实 `.habitpack`。

M1 仍应停留在本分支。只有负责人确认第二轮方向后，才把验证成立的产品决定同步到 `main`。[D-024]
